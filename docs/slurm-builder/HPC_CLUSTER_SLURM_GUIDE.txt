PLAKSHA HPC CLUSTER: SLURM JOB-SCRIPT REFERENCE
================================================

Snapshot date: 2026-08-19 (Asia/Kolkata)
Cluster name: plakshahpc
Slurm version: 25.11.4

Purpose
-------
This document summarizes the Slurm resources and policies that users need when
writing batch scripts. It can also be supplied to ChatGPT together with a
program's resource requirements so that it can suggest suitable #SBATCH lines.

Configuration can change. Before submitting important jobs, check the live
values with:

    sinfo
    scontrol show partition
    scontrol show node
    sacctmgr show user "$USER" withassoc format=User,Account,Partition,QOS,DefaultQOS


QUICK SELECTION GUIDE
---------------------

1. Choose a partition (hardware):

   rtx   Default partition. Use for GPU jobs needing an RTX GPU slice and for
         CPU-only jobs unless an administrator recommends otherwise.

   h200  Use only when the job needs an NVIDIA H200 NVL GPU or the resources
         of the H200 node. Access is restricted to paid and faculty QoS.

2. Choose a QoS (policy/entitlement):

   Use the DefaultQOS assigned to your Slurm account unless you have explicitly
   been granted another QoS. Check your own assignment with the sacctmgr command
   above. Request a non-default tier with:

       #SBATCH --qos=<qos-name>

3. Request only what the program needs. A larger CPU, GPU, memory, or time
   request may wait longer in the queue.

Memory and CPU notes applying to both partitions
------------------------------------------------

  * Slurm allocates consumable CPUs and memory (SelectTypeParameters is
    CR_CPU_MEMORY). CPU counts above are logical CPUs/hardware threads as Slurm
    reports them.
  * The cluster-wide default memory is 8192 MB per requested CPU. Explicitly
    request memory to make the intended allocation clear, using either
    --mem=<memory per node> or --mem-per-cpu=<memory> (do not use both).
  * No swap is allowed for jobs, and RAM limits are enforced by cgroups. A job
    that exceeds its requested memory may be killed for out-of-memory use.
  * Node-local temporary disk is not advertised as a Slurm resource (TmpDisk=0).
  * No node features/constraints are currently defined. Select GPU hardware by
    partition and typed --gres rather than with --constraint.
  * A job may span multiple nodes, but each partition is small: h200 has one
    node and rtx has two. Multi-node jobs must use software configured for
    distributed execution; requesting multiple nodes does not automatically
    make an ordinary program parallel.


QOS POLICIES
------------

The limits below are QoS limits. Partition limits also apply, and the effective
limit is the more restrictive applicable limit. "GPU/user" is the maximum
number of allocated generic GPUs across that user's running jobs in the QoS.
"Running jobs/user" and "submitted jobs/user" are likewise per-user limits.

QoS        Priority  Max time  GPU/user  Running/user  Submitted/user  Flags
---------  --------  --------  --------  ------------  --------------  ---------------------
paid           1000  7 days    8         20            200             DenyOnLimit
faculty         600  5 days    8         20            200             DenyOnLimit
rfphd           400  5 days    4         10            100             DenyOnLimit
course          200  12 hours  1          2             10             DenyOnLimit
general         100  12 hours  1          2             10             DenyOnLimit
scavenger         0  4 hours   none set   8             50             DenyOnLimit,NoReserve

Important eligibility and behavior:

  * QoS access comes from the user's/account's Slurm association. The fact that
    a QoS exists does not mean every user may select it.
  * h200 accepts only paid and faculty.
  * rtx accepts paid, faculty, rfphd, course, general, and scavenger.
  * paid, faculty, rfphd, course, and general can each preempt scavenger jobs.
    They do not preempt one another. scavenger cannot preempt any QoS.
  * Preemption mode is REQUEUE, with a cluster-wide 10-minute preemption-exempt
    period. Applications should checkpoint where practical and scripts should
    tolerate restart. Cluster jobs are requeue-enabled by default.
  * Every operational QoS uses DenyOnLimit: a job that would breach a QoS limit
    is rejected rather than left pending. scavenger also uses NoReserve, so its
    jobs cannot reserve resources through backfill scheduling.
  * Priority is multifactor. QoS priority and fair-share have substantial
    weights, so queue order is not determined only by submission time.

The "normal" QoS also exists internally, but it is not allowed by either user
partition and should not be requested for ordinary work.

ACCOUNTS
---------------

Slurm accounts identify the allocation or credit pool charged for a job. They
are separate from QoS, which controls priority, wall time, preemption, and job
limits.

The cluster uses this account-association model:

    root
    |-- courses
    |   |-- course_user_1
    |   `-- ...
    |-- faculty
    |   |-- faculty_user_1
    |   `-- ...
    |-- rfphd
    |   |-- rfphd_user_1
    |   `-- ...
    |-- general
    |   `-- general users
    `-- paid
        `-- direct users, when assigned

Users are associated directly with the applicable allocation account. In
particular, each faculty member is a user under faculty; there is no separate
per-faculty-member sub-account. Paid jobs use the paid account itself. Do not
use hypothetical paid-* account names in job scripts.

QoS permissions are inherited from the parent association and augmented by the
child account's own tier. The common parent grants general and scavenger; each
allocation child adds its tier-specific QoS. The effective choices are:

Account    Effective permitted QoS              Default QoS
---------  -----------------------------------  -----------
general    general, scavenger                   general
courses    general, scavenger, course           course
faculty    general, scavenger, faculty          faculty
rfphd      general, scavenger, rfphd            rfphd
paid       general, scavenger, paid             paid

For example, a user associated with courses can submit against that account
with course (the default), general, or scavenger:

    sbatch --account=courses --qos=course job.sh
    sbatch --account=courses --qos=general job.sh
    sbatch --account=courses --qos=scavenger job.sh

Likewise, a faculty user selects the faculty allocation account and may choose
faculty, general, or scavenger according to the job's needs:

    sbatch --account=faculty --qos=faculty job.sh

The selected account determines which allocation is charged. The selected QoS
determines scheduling policy and must be in that association's effective QoS
set. Omitting --qos uses the account's DefaultQOS.

A user's live association output remains authoritative:

    sacctmgr show user "$USER" withassoc format=User,Account,QOS,DefaultQOS

Account permission does not override a partition's AllowQos list. scavenger is
allowed on rtx, but h200 accepts only faculty and paid QoS.

SBATCH TEMPLATES
----------------

RTX: one 24 GB GPU instance

    #!/bin/bash
    #SBATCH --job-name=my_job
    #SBATCH --partition=rtx
    #SBATCH --qos=general             # change/remove according to your account
    #SBATCH --gres=gpu:1g.24gb:1
    #SBATCH --nodes=1
    #SBATCH --ntasks=1
    #SBATCH --cpus-per-task=4
    #SBATCH --mem=32G
    #SBATCH --time=01:00:00
    #SBATCH --output=slurm-%j.out

    # Load the site's required environment/modules here, then use srun:
    srun python my_program.py

CPU-only, single process

    #!/bin/bash
    #SBATCH --job-name=cpu_job
    #SBATCH --partition=rtx
    #SBATCH --qos=general             # change/remove according to your account
    #SBATCH --nodes=1
    #SBATCH --ntasks=1
    #SBATCH --cpus-per-task=8
    #SBATCH --mem=32G
    #SBATCH --time=01:00:00
    #SBATCH --output=slurm-%j.out

    srun python my_program.py

The numbers in these templates are examples, not recommendations for every
program. Match --cpus-per-task to the program's real thread count, --mem to its
measured peak RAM plus a modest margin, and --time to expected runtime plus a
margin. Do not request a GPU for code that cannot use one.


USEFUL LIVE CHECKS
------------------

Show partition/node availability:

    sinfo -o "%P %N %a %t %c %m %G"

Show full partition or node configuration:

    scontrol show partition
    scontrol show node

Show your account, permitted QoS, and default QoS:

    sacctmgr show user "$USER" withassoc format=User,Account,Partition,QOS,DefaultQOS

Validate a script without submitting it (when supported by the installed
sbatch version):

    sbatch --test-only job.slurm

Inspect why a submitted job is pending:

    squeue --me --start
    scontrol show job <job-id>

Inspect completed-job resource use to tune later requests:

    sacct -j <job-id> --format=JobID,State,Elapsed,AllocCPUS,ReqMem,MaxRSS,AllocTRES


INFORMATION TO GIVE CHATGPT FOR A JOB-SCRIPT RECOMMENDATION
----------------------------------------------------------

Supply this file plus the following facts. Do not include secrets, passwords,
API keys, private datasets, or credentials.

  * Your permitted QoS and DefaultQOS from the sacctmgr command above
  * The command that runs the program
  * Whether it is CPU-only or GPU-enabled
  * Required GPU type and GPU memory, if known
  * Number of processes, CPU threads per process, and whether it is multi-node
  * Estimated or previously measured RAM and runtime
  * Whether the program can checkpoint/restart after preemption
  * Relevant framework (for example PyTorch, TensorFlow, MPI, OpenMP)
  * Input size and how resource use scales with it

Suggested prompt:

    Using the attached Plaksha HPC Slurm reference and my code/run command,
    recommend a conservative but efficient Slurm batch script. Explain the
    partition, QoS, GPU GRES, CPU, memory, task, node, and time choices. Do not
    invent cluster options. Point out anything that must be measured or checked
    with the administrator. My permitted QoS/default is: [...]. My run command
    is: [...]. My workload details are: [...].

----------------

scontrol show node, scontrol show config, and sacctmgr show qos/assoc. Transient
node states and free memory were deliberately omitted because they quickly
become stale. Individual usernames and membership lists are also omitted; users
should query their own association instead.
